# ADR 0001: Bounded, header-only Safetensors inspection

**Status:** Accepted for the initial metadata inspector. **Date:** 2026-11-24.

## Context

The first model-file task is metadata inspection without loading tensor payloads. Upstream Safetensors uses an eight-byte little-endian header length, a UTF-8 JSON header, and a raw data buffer. Tensor entries include dtype, shape, and half-open payload offsets. The Rust `SafeTensors::read_metadata` API validates against a complete file slice, including payload length; requiring a full-file read would conflict with the bounded-inspection objective. Sub-byte dtypes also require bit-level size arithmetic and byte-alignment checks. See the source-backed [Safetensors inspection note](../../research/safetensors-inspection.md).

## Decision

Add a cohesive `qml-model` crate with a read-only seekable-reader API. It reads the eight-byte prefix and at most 16 MiB of JSON header, seeks to determine file size, then validates that the tensor ranges exactly and contiguously account for the declared data buffer. It rejects duplicate JSON keys, unknown fields and dtypes, excessive tensor counts or ranks, arithmetic overflow, byte-misaligned tensors, invalid offsets, holes, overlaps, and trailing/uncovered payload bytes. The CLI exposes `qml inspect-safetensors PATH` and `qml inspect-safetensors --json PATH`.

The 16 MiB project cap is intentionally stricter than the 100 MiB maximum documented by upstream. It is a QML resource policy, not a format limit. A caller may lower the cap but cannot raise it through this API. The parser does not read tensor values, validate their numerical contents, load models, or make claims about model architecture or behavior. The original input is opened read-only and remains unchanged.

The pinned Safetensors 0.8.0 crate is test-only and serves as a differential parser oracle for generated fixtures. Runtime parsing remains in Rust using `serde` and `serde_json`; this keeps a future full-file decoder distinct from metadata-only inspection. Synthetic tests use generated bytes, not third-party weights or datasets.

## Alternatives considered

- **Read the full model file and call upstream `read_metadata`:** rejected for this command because it reads/holds the entire file and can require memory proportional to model size.
- **Memory-map the entire model and call upstream:** deferred. Mapping can still impose address-space and platform-specific constraints, and the requested initial operation needs only the bounded header. A later payload reader can separately assess mapping/streaming and preserve upstream validation.
- **Parse a generic JSON value:** rejected because ordinary map deserialization can silently overwrite duplicate keys. A typed visitor rejects duplicates before they become ambiguous.
- **Accept unknown dtypes or future fields:** rejected. The metadata arithmetic depends on known bit widths; guessing could misreport tensor sizes. Unknown representations fail explicitly until deliberately supported.

## Validation

The parser has unit tests for scalar and zero-sized tensors, sub-byte alignment, metadata, duplicate keys and fields, unknown fields and dtypes, overflow, invalid offsets, data gaps and trailing payload, truncation, resource limits, deterministic ordering, and a reader that errors if the parser attempts to read payload bytes. Property tests generate valid U8 shapes. Integration tests compare generated F32 and F4 fixtures to the pinned upstream parser. No pretrained model is required.
